## Inspiration

I designed TradeProof for a small business that orders samples or a small batch from an overseas supplier. In that
situation the quote may arrive in Chinese, English or both, and it can differ from the request in ways that are easy
to miss in a chat thread: a different quantity, a cheaper steel grade, a fee that is not mentioned, or a deposit the
buyer never agreed to. If the payment is then made as a separate step, nothing shows which quote and which conditions
it was meant to settle. I wanted the payment to be the last step of a traceable decision, not a separate action. This
customer and these situations are my design hypothesis — no user research has been done yet.

## What it does

TradeProof carries one cross-border purchase from request to PayPal payment on a single record:

1. **Request** — items, specification, quantity, budget, ship date and accepted payment terms, with revision history.
2. **Quote versions** — the supplier's quote is pasted as text and saved as an immutable version, together with a
   snapshot of the request it answered.
3. **AI extraction with sources** — a model proposes values, each with a verbatim source excerpt. A value is kept only
   if its excerpt is found in that quote version's text (for verbatim facts, with the value inside it). Fields the
   quote does not state stay *unknown*; values with a missing, unmatched or unreadable excerpt are not saved as facts
   and the run is marked incomplete. The buyer reviews each value one by one.
4. **Deterministic comparison** — code (not AI) compares the quote with the request. Fees the quote does not state
   stay *unknown*, never zero.
5. **Bilingual clarification** — English / 简体中文 questions from fixed templates; the supplier's replies are stored
   and the buyer records which question each reply answers. Nothing is sent automatically, and an answer is never an
   approval.
6. **Approval of exact conditions** — only the approver the buyer assigned can approve. The approval binds one quote
   version, one extraction run and the reviewed values. It stops being valid when something it was based on changes —
   for example a request revision that changes the compared request content, a newer quote version, changed reviews
   or requirement classifications, a change in the recorded supplier statements, or removal of the approver's
   assignment. Editing only the request title does not invalidate it.
7. **Payment bound to the approval** — the server creates a PayPal order for exactly the approved USD amount (the
   browser cannot set it), captures it and verifies the result server-side.
8. **AI Copilot** — five fixed buttons that explain the record's stored facts with citations ("what is still open?",
   "can I pay?"). It cannot approve, pay or change anything.

**Boundaries of this version:** the default local run for judges and the demo video use **MOCK mode** (simulated
PayPal, canned AI output, no keys); real Claude calls and real PayPal Sandbox payments need the user's own keys and
were tested separately. Payments are PayPal **Sandbox** only (no PayPal Live mode, no real money). The payee is one
fixed Sandbox test merchant from the server configuration — not the supplier. TradeProof is **not escrow** and never
holds money. Quotes are pasted as text. One full USD amount is paid once; deposits are blocked.

## How we built it

- **Next.js 16 / React 19 / TypeScript**, with all business rules in server-only modules and **SQLite** through
  Node's built-in `node:sqlite` (forward migrations with automatic backups; append-only review, approval and payment
  events).
- **PayPal:** Orders v2 via `@paypal/paypal-server-sdk` in the Sandbox — create, capture and server-side GET
  verification. An unknown PayPal result is treated as neither success nor failure: it is recorded and checked by
  reading PayPal first. A capture whose result is unknown is never sent again; an order creation with an unknown
  result is not retried automatically — the buyer may repeat it with the same `PayPal-Request-Id`, only within 5 hours
  of the first attempt. The payee is a fixed Sandbox test merchant from the server configuration.
- **AI (Anthropic Claude):** quote extraction and Copilot explanations. Every real call goes through a local budget
  ledger (reserve before the call, settle after, per-day and total limits). Model output is checked before it
  counts: an extracted value is kept only if its excerpt is found in the quote text (values that fail stay visible,
  marked as not saved), and a Copilot answer that fails its checks against stored facts is not shown.
- **Access control:** preset local accounts, server sessions, CSRF protection, per-request ownership and approver
  grants checked on every page and API.
- **Safe MOCK mode** so anyone can run the full flow without keys: separate database, canned SYNTHETIC extraction,
  MOCK Copilot answers and simulated PayPal; it refuses to start if a real model, real payments or the main database
  would be used.

## How we used AI

- **In the product — Anthropic Claude API** (`@anthropic-ai/sdk`; model `claude-sonnet-5-5` in the recorded real
  runs): extracts structured values with source lines from pasted supplier quotes, and writes the Copilot's
  explanations of a record's stored facts. It proposes and explains; it never decides approval state, amount or
  payment. Every real call is budgeted and its output checked before it counts or is shown.
- **Planning and review — ChatGPT** (OpenAI): I used ChatGPT for project planning, refining requirements, writing
  acceptance checklists, drafting prompts and reviewing the written materials. It was not used to run the local
  repository or its tests.
- **During development — Claude Code** (Anthropic's AI coding assistant): I built TradeProof with Claude Code, which
  did much of the local implementation, tests, documentation and the video production workflow under my direction.
  I set the requirements, made the product and safety decisions, authorised each step and did the manual acceptance.
- **In the demo video — Kokoro-82M**, run locally: offline text-to-speech for the narration (synthetic voice; no
  cloud TTS).
- **MOCK vs real:** the video and the judges' local run use MOCK extraction, MOCK Copilot answers and simulated
  PayPal. Real-model extraction (25 Oct), real Copilot cases (2 Nov) and real PayPal Sandbox payments (21 and 30 Oct)
  were separate, earlier tests.

## Challenges we ran into

- **Keeping AI output honest:** a value without a source line, or a source line that does not appear in the quote,
  must not look like a fact. I built evidence checks and kept failed runs visible as *incomplete* instead of hiding
  them.
- **Binding payment to a decision:** approvals had to be immutable snapshots that become invalid when something they
  were based on changes (for example a request revision that changes the compared content, a newer quote version, a
  changed review or classification, or removal of the approver's assignment) — and payment had to re-check that
  inside the same transaction.
- **Unknown outcomes and idempotency:** a timed-out PayPal call may or may not have succeeded. TradeProof records the
  result as unknown, checks it by reading PayPal and never blindly captures again; the only repeat it allows is the
  buyer re-sending an order creation with the same `PayPal-Request-Id` within 5 hours (PayPal keeps request ids for
  6 hours).
- **Honest demos:** separating what was shown in MOCK mode from what was tested with a real model or the real
  Sandbox, everywhere it is presented.

## Accomplishments that we're proud of

- A complete request → quote → review → clarification → approval → payment flow on one traceable record.
- Real PayPal Sandbox payments verified server-side (USD 1.00 on 21 Oct; USD 12.00 after a human approval on 30 Oct).
- Real-model extraction of five SYNTHETIC quotes with source checks, and authorised real Copilot runs validated
  against stored facts.
- A MOCK mode that lets judges run everything locally with no keys and no external calls.

These real tests were separate; TradeProof has **not** been verified as one real end-to-end AI → approval → PayPal run.

## What we learned

- Deterministic code should own every decision that moves money; AI is most useful when it reads, cites and explains.
- "Unknown" must be a first-class value — treating a missing fee as zero is how bad payments happen.
- An approval is only meaningful if it is bound to the exact version of what was approved.

## Testing instructions (for judges)

The supported judge run is **MOCK mode**: simulated PayPal and canned AI output — no PayPal or Claude call is made,
and no API keys or shared credentials are needed. Clone the repository and follow the README's **Run it locally**
section: `npm ci`, `npm run mock:accounts` (you choose the three passwords), optionally `npm run mock:seed-base`, then
`npm run mock:start` and open <http://127.0.0.1:3000>. The 20-step walkthrough is in `docs/demo-script.md`.
Tested on Windows 11 with Node.js 24.19.0; requires Node.js 22.18 or newer. Production serving (`npm start`) is not
supported — use the local dev server as described.
