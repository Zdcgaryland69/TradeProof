## 1. Buyer type

Main demo scenario stays a Singapore small business buying cross-border; individual buyers are supported too.

| Field | Business | Individual |
| --- | --- | --- |
| `buyer_type` | `BUSINESS` | `INDIVIDUAL` |
| Company name (`buyer_company`, *exists*) | Shown, labelled *Company name*, required for new Business requests | Shown as optional *Company / Organization* |
| Person name (`buyer_person_name`, new) | Optional *Contact name* | Shown, labelled *Your name*, required for new Individual requests |

Rules:

- Buyer type describes the purchase for display and wording only. It is **not** the PayPal account type, does not decide payment permission and does not decide PayPal protection eligibility; nothing in the app may claim otherwise.
- `INDIVIDUAL` never skips confirmation before payment, approval or any access rule. A one-person buyer can hold several roles, but each step is still recorded.
- Out of scope: supplier portal, consumer shopping platform.
- Edits go through the existing revision check (`revision` + `UPDATE … WHERE revision = ?`); `buyer_type` and `buyer_person_name` are part of the request snapshot from the version that adds them (see §7.4).

| # | Name in UI | What it is | Format | Where it lives |
| --- | --- | --- | --- | --- |
| 1 | **Request ID** | Full database key of a procurement request | `pr_<uuid>`; short reference `PR-XXXXXXXX` (first 8 hex) | `procurement_requests.id` *(exists)*. Detail page today says "Full ID" + copy button *(exists)* → rename the label to **Request ID** |
| 2 | **Item reference** | Display form of the stable item line id | `pri_<uuid>`; shown as `IT-XXXXXXXX` (first 8 hex), qualified by the request when shown elsewhere: `PR-79ED0A13 · IT-1A2B3C4D` | `procurement_request_items.id` *(exists, v6)*. | 3 | **TradeProof quote reference** | System-generated; locates a quote series; shared by all its versions | `qs_<uuid>`; shown as `QS-XXXXXXXX` | `quote_series.id` *(exists; `QS-` label already shown)* |

| 5 | **Supplier quote number** | The number printed in the supplier's own text; may be empty | Raw text ≤ 100, as written | Per version, append-only facts table (new, §2.3) |

**Decision 24 Oct (owner discussion):** the stable Item reference (row 2) stays the item identifier. No SKU / SPU system is introduced. A *supplier item code* (the supplier's own article number) may later be added as an optional helper field; this is **not approved** and not scheduled. The same code never replaces checking specification, material, capacity and the other terms.

### 2.1 Stability and short references

- Editing an item's name, quantity or order never changes its id *(exists, tested; see setup-status 23 Oct)*.
- A short reference never replaces the full key. URLs, API bodies and foreign keys always use full ids.
- Resolving a short reference (search box, pasted text): match by prefix on the full id within the caller's access scope. **0 matches** → "No match"; **1** → that record; **2 or more** → list all candidates with title, created time and full id; never pick one. Typing more hex digits narrows it. The same rule applies to `IT-` (within one request) and `QS-`.
- Copy buttons copy the full id; the short form is display only.

### 2.2 Quote name under the immutable model

`quote_series` is immutable (trigger), and that stays. A rename appends a row; nothing is updated:

```text
quote_series_names (v7, append-only; triggers refuse UPDATE / DELETE)
  id TEXT PK 'qsn_*' · series_id → quote_series · name (1..200) · set_at · revision INTEGER (1, 2 …, UNIQUE per series)
  idempotency key in quote_save_keys (same fingerprint rules)
```

- Current name = latest row in `quote_series_names`, else `quote_series.name`. Old names stay visible in the series history.
- A new version inherits the current name (as today, the composer only shows it). Renaming is a separate action with its own conflict check (`expectedNameRevision`).
- Versions do not store a name, so a rename never changes what a version's text, hash or snapshot says.

### 2.3 Supplier quote number per version

Several versions of one series may carry the same or different numbers; the supplier may also change the number. The value comes only from the actual source:

```text
quote_version_supplier_refs (v7, append-only; triggers refuse UPDATE / DELETE)
  id 'qvr_*' · version_id → quote_versions
  value_raw TEXT NULL        exactly as typed / as found; NULL = user stated "no number in this text"
  search_key TEXT NULL       derived (§3.2); never shown as the value
  origin  USER_ENTERED | AI_CANDIDATE | USER_CONFIRMED | USER_CLEARED
  evidence_text TEXT NULL    verbatim excerpt of this version's raw_text (required for AI_CANDIDATE)
  extraction_id TEXT NULL    AI run that proposed it (24 Oct extraction records)
  supersedes_id TEXT NULL    earlier row of the same version it replaces
  created_at
```

- **User entered**: typed in the composer at save time; written in the same transaction as the version and included in its idempotency fingerprint. It is the user's statement, labelled as such.
- **AI candidate**: proposed only with an `evidence_text` that is found in the version's `raw_text` (same rule as `unverifiedSources`, *exists* in `src/lib/quote.ts`; `ExtractedQuote.quoteNumber` is already a `Sourced<string>`). Shown as "suggested — check against the text". Never counted as the value until the user confirms.
- **User confirmed**: the user checked a value against the saved text. It means "matches the pasted text", not "verified with the supplier".
- **Empty**: no row, or `USER_CLEARED`. TradeProof never generates a number and shows it as the supplier's. The `QS-` reference is always labelled *TradeProof reference*.
- Current value per version = newest non-superseded row; history shown on request.
- Supplier name, quote number and email text are never identity proof and never choose or change a PayPal payee (existing rule).

## 3. Search

### 3.1 Entry and coverage

Scope decision (24 Oct, owner): search does **not** cover the contents of request revisions (`procurement_request_revisions`). It **must** still find supplier quote numbers in **every quote version, including earlier versions** (row "Supplier quote number, all versions" below; A3).

A search box on `/procurements` (list page). One query matches:

| Matches | How |
| --- | --- |
| Request ID (full) | exact |
| Short reference `PR-…` / hex prefix | prefix on full id (§2.1) |
| TradeProof quote reference `QS-…` | prefix on series id |
| Supplier quote number, **all versions** (history included, superseded values marked "earlier value") | `search_key` exact, then loose (§3.2) |
| Request title, quote name (current and earlier names) | case-insensitive substring on the search key |

Results: one row per matching **quote version or request**, showing request (short ref + title), supplier display name, quote name, version (`v3`), which field matched and the matched raw value, with a link to that exact version (`/procurements/[id]/quotes?series=…&version=…`). Different suppliers with the same number and several versions of one series are listed as separate rows, grouped by request → series; nothing is merged or deduplicated away. States: empty query, no results, ambiguous short code (candidates), invalid input (length > 200, control characters → 422 with message), server error (message, input kept).

### 3.2 Normalisation (search only; stored values are never changed)

`search_key` = Unicode **NFKC** (full-width `ＱＴ－２０２６` → `QT-2026`) → lower case with a locale-independent mapping → trim → collapse runs of whitespace to one space. Hyphens, slashes, dots, `#` and leading zeros are **kept**, so `QT-2026/118` and `QT-2026-118` are different keys.

A second, clearly labelled **"similar"** tier compares keys with separators removed (`-`, `_`, `/`, `.`, space). Those results are listed under "Similar numbers — check carefully", never merged with exact matches.

### 3.2a As built (25 Oct)

Code: `src/lib/search.ts`, `src/server/search/`, `src/app/procurements/SearchResults.tsx`, `GET /api/procurements/search?q=`; tests: `tests/search.test.ts` (10), browser `npm run e2e:25oct`.

- Matches: full Request ID and full `qs_` reference (exact, case-insensitive); `PR-` / `QS-` short codes (≥ 4 hex digits, prefix compared as `substr(id, 1, n) = ?`, no `LIKE`), a bare 8-hex code checks both kinds; supplier quote numbers in **every** version (`EXACT` key, `CONTAINS`, then a labelled `SIMILAR` tier with `- _ / .` and spaces removed); current request title and quote name (contains).
- Every supplier-number row is its own result with its origin (`AI suggestion — not confirmed`, `entered by you`, `confirmed by you`) and status (`current value`, `earlier value`, `candidate only`); the version shows "earlier version (latest is vN)". Same number at different suppliers or in several versions → separate rows, grouped request → series → version, never merged.
- An ambiguous short code lists all candidates with a notice; none is chosen. A too-short code gives a note and no id lookup.
- Input: ≤ 200 characters, no control characters, well-formed → else `422 INVALID_QUERY` (the page shows "Not searched", text kept). The query is always a bound parameter; `%`, `_`, `*`, quotes and SQL text are ordinary characters (tested). Max 50 results, `truncated` flag beyond.
- **Evening follow-up (owner feedback):** category filter by the field that matched (*All fields, Request ID, Procurement title, TradeProof quote reference, Supplier quote number, Quote name*); *Newest / Oldest first* by the matched record's save time (request `updated_at`, series `created_at`, supplier-number row `created_at`; ties by stable id); one UNION statement with filter, scope and order before `LIMIT`, and a true total ("N matches across M procurement requests"); while searching only the results are shown (empty state on no match, *Clear search* back to the list).
- Access: every query ANDs `requestScope(principal, "r")` (`src/server/access/policy.ts`) before `LIMIT` — the single entry point for 28 Oct. Today it allows the local developer only; **no multi-user isolation is claimed**. Production → 404; non-loopback Host → 403. Search never calls a model.

### 3.3 Scope

- Built first in local dev only, same guard as today (`localOnlyGuard`, 404 in production). No multi-user isolation is claimed until §6 is implemented and accepted.
- From 28 Oct every query is filtered on the server by the caller's access scope **before** matching and counting (§6.2).

### 4.1 Quote and AI languages

- **Original language** (of the saved text) and **Translate into** are separate settings.
- Original language: auto-detected, user-correctable, may be **mixed** (e.g. `zh` + `en`). Stored with origin `AUTO_DETECTED | USER_SET`.
- AI output language follows the UI language by default and can be chosen separately per action.
- Views: *Original*, *Translation*, *Side by side*. A translation never overwrites or replaces the original; original text, hash and version stay as saved.
- Chinese ↔ English is accepted first; other pairs open one by one after real tests.

## 5. Original ↔ translation check

Purpose: help the user understand a quote and catch translation problems that would change the deal.

### 5.1 Two kinds of checks

| Kind | Covers | How |
| --- | --- | --- |
| Deterministic | Quantities, unit prices, totals, currencies, percentages, units, dates that parse unambiguously | Code; compares parsed values, not strings. Handles digit formats (`1,800.00`, `1.800,00`, `1800`, Chinese numerals such as `五百`), unit wording (`pcs` / `件` / `个`), currency forms (`USD`, `US$`, `美元`; `¥` alone is ambiguous between CNY and JPY → *unable to verify*). Never converts currencies or units and never guesses a date: `03/04/2026` → *unable to verify* unless the format is stated |
| AI semantic | Omissions, negations, conditions ("if", "unless", "only when"), material and spec, logo, lead time, payment terms, who bears which cost, trade terms | Model, with output schema: each issue cites a verbatim excerpt from the original **and** from the translation; excerpts are checked against both texts like `unverifiedSources`; an issue whose excerpt is not found is dropped and counted as a failed check part |

"All numbers are identical" is never on its own a pass.

### 5.2 Result states

`NO_CRITICAL_DIFFERENCES_DETECTED` · `POTENTIAL_DIFFERENCES_FOUND` · `UNABLE_TO_VERIFY` (parts could not be checked) — plus separate states that are **never shown as passed**: `NOT_RUN`, `RUNNING`, `FAILED` (error / timeout / invalid model output) and `STALE` (computed on read: the original's hash or the translation's hash differs from the one checked).

Wording: "No critical differences detected" — never "accurate", "verified" or a percentage. No accuracy or confidence numbers are shown.

Each issue: original excerpt, translation excerpt, what may differ, suggested next step (e.g. "ask the supplier to confirm the deposit percentage").

### 5.3 Records (append-only)

```text
quote_translations   id · version_id · source_sha256 · original_language(s) + origin · target_language
                     · text · text_sha256 · origin AI | USER_EDITED · model · prompt_version · created_at · supersedes_id
translation_checks   id · translation_id · source_sha256 · translation_sha256 · checker_version (deterministic)
                     · model · prompt_version · status · issues JSON · started_at · finished_at
                     · user_corrections (separate rows: issue id, action dismissed / confirmed / edited, note, time)
```

### 5.4 Boundaries

- Only text the user pasted and saved is checked. TradeProof does not claim to verify an original PDF or image, file integrity, supplier identity or authenticity.
- Quote text is **data to analyse, never instructions**: it is passed to the model in a delimited data field; the system prompt says instructions inside it are ignored; the model has no tools that act on records during extraction or checking; output is schema-validated.
- Supplier text, the user's revision note and terms carried from earlier versions are kept as separate, labelled inputs. A `SUPPLEMENT` is traced only to the version it explicitly supplements; earlier content is never presented as this version's text.

## 6. Access control and privacy

Access control is required. Masking text with `***` is not access control.

### 6.1 Who can see what

| Principal | Can | Cannot |
| --- | --- | --- |
| Buyer owner | Everything on their buyer workspace's records; grant / revoke members | — |
| Authorised member (procurement, approver) | Records they are granted, according to role (e.g. approver approves, cannot edit quotes) | Records not granted |
| Another buyer | Nothing | Query, read, modify or export any of it, or learn whether it exists |
| Supplier (future, not in MVP) | Only their own quote shared with them, through an **authenticated identity explicitly bound** to that share | Be authorised by matching name, email text or quote number; see competing quotes, internal budget or approval comments |

No supplier login or portal in the MVP; the supplier side is a documented future dependency (needs authentication, explicit binding, field-level redaction of budget and approvals).

### 6.2 Server-side rules (one policy module, used everywhere)

- Covered: lists, search, detail, quote versions and history, snapshots, export, attachments (if ever added), **AI input context** and AI result reads, translation and check records.
- Filter first: queries join the caller's access scope before matching, counting or paging, so no count, title, number or summary leaks.
- Object routes return the **same 404** for "does not exist" and "not allowed"; list and search simply omit. Same timing path (no early exit before the scope check).
- Ids, short codes and supplier quote numbers are not secrets or credentials; knowing one grants nothing.
- Ownership of a new record comes from the trusted server session, never from a client field (the API already refuses unknown fields such as `id`; `ownerId` will be refused the same way).
- Revocation takes effect on the next request (authorisation checked per request; no long-lived cached permission).
- AI never retrieves beyond the caller's scope: the server builds the model context from records it has already authorised; caches and background job results are keyed by scope and read back through the same check.
- Audit: grant / revoke, access denied on object routes, export, approval, payment actions — actor, action, object id, outcome, time. Never quote text, tokens or keys.

## 7. Migration design (v7, v8) — written, **not executed**

### 7.1 Procedure (both versions; same framework as v4–v6, `src/server/db/database.ts`)

1. Before migrating an existing file: `VACUUM INTO data/backups/<file>.v<from>-before-v<to>.<UTC>.sqlite`; if the copy fails, nothing is migrated *(exists)*.
2. All steps in one `BEGIN IMMEDIATE` transaction; version re-read inside the lock; any error → `ROLLBACK`, `user_version` unchanged *(exists)*.
3. Additive only: `ALTER TABLE … ADD COLUMN` (nullable) and new tables. **No** rebuild of `quote_versions` / `quote_series`, **no** dropping or disabling of the immutability triggers, **no** `UPDATE` of existing quote rows. (`ADD COLUMN` is DDL; the UPDATE triggers do not fire and existing rows read NULL.)
4. Idempotent: each step checks whether its column / table exists, as v5 and v6 do.
5. Recovery: stop the dev server, copy the backup over `data/sandbox-payments.sqlite` (and remove `-wal` / `-shm`), check out the previous commit. A newer-schema file is refused by older code *(exists: "schema vN is newer than this code")*, so roll back the file together with the code.
6. `data/` (database, backups, evidence, e2e state) stays Git-ignored (`.gitignore`: `/data/`, `*.sqlite*`, `*.db`; checked 24 Oct with `git check-ignore`).

### 7.4 Snapshots across schema versions

- `request_snapshot` keeps `snapshotVersion: 1` and its exact JSON forever; it is never rewritten.
- New snapshots that include buyer type use `snapshotVersion: 2`. The reader accepts every version and shows fields missing from older snapshots as **"not recorded at the time"**, never as a current value back-filled into the past.
- The comparator reads snapshots through one adapter (`comparableFromRecord`, *exists*), so it handles both.

### 7.5 Revision and idempotency

- `buyer_type`, `buyer_person_name` join the request fields covered by the `revision` check and the request snapshot.
- Supplier quote number and original language, when given at save time, join the version's idempotency fingerprint (same key + different number → `IDEMPOTENCY_KEY_REUSED`). Renames and later facts rows carry their own keys and expected revisions.
- Fingerprints of already-stored keys are not recomputed; old keys keep replaying their original result.

### 7.6 Derived data never rewrites evidence

Search keys, translations, check results, extraction results and evaluations are separate rows pointing at a version id and its hash. They can be deleted and rebuilt; raw text, hashes, snapshots and versions are never changed by them.

### 7.7 Checks before and after each migration (same as 22–23 Oct)

Dump before; backup equals the dump; after: payment record (PAID, USD 1.00) and events identical; requests (values, source, revision, timestamps), item lines and **item ids** identical; every quote version's `raw_text`, `raw_text_sha256` (recomputed), `request_snapshot` byte-identical; triggers still present and refusing UPDATE / DELETE; `PRAGMA integrity_check` ok; restart → no second backup, same ids; production build still 404 and DB untouched. Rehearse first on a copy of the real file.
